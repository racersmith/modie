Define data models, filesystem traversal algorithms, and schema parsers for Canon primitives artifacts (`MOTIVATION`, `RULE`, `ADR`, `GIST`, `TASK`) independent of any specific CLI or transport protocol.

`MOTIVATION` is a composable document that can be placed anywhere in a project that describes why the subsequent content exists. When context is needed from a location within a project, the `MOTIVATION` documents can be combined from the starting location up to the root of the project. Providing agents with compact and token efficient context as needed. These documents are the slowest to change. These documents do not reference other documents.

`RULE` documents provide a single falsifiable claim that the system adhere to. Short codes to these documents allow for them to referenced from code and tests in such a way that refactoring does not break the documentation. The location of these documents reflect their area of influence in the codebase. Thus a `RULE` document in the `database` directory governs the database and any packages that depend on it. These documents are slow to change and should be independent of the implmentation details such that if the project were to be rewritten in a different language, they would remain valid.

`ADR` documents provide context for a architectural or design choice. Allowing for agents to look up the reasoning for a design choice and apply it to new or refactored code. These documents live in the same directory as the code that they most directly influence, and have the same ancestry as the files that they influence. These documents should be rare in a project and are point-in-time decisions. `RULES` downstream of these decisions may be impacted if this decisions were to be changed.

`GIST` documents are the executive summary of the specific implmemtnation chosen to satisfy a set of `MOTIVATION`, `RULE`, and `ADR` documents. The location of these documents reflect their area of influence in the codebase. The motivation for these documents is to allow agents to quickly understand the codebase without having to parse the entire codebase. These documents never reference any other records.

`TASK` documents are ephemeral and are used to plan implmentation of the project. These are scoped to their location within the project. This allows for fast contextual understanding of the task by querying the `MOTIVATION`, `RULE` and `ADR` records within their scope. `TASK` documents have unique IDs so they can be referenced bewteen tasks for planning purposes. These documents can reference `MOTIVATION`, `RULE` and `ADR` records to gather context to satisfy the task.
